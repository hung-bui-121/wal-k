# ADR-0007 — Canonical Skill Registry & Provider Projections

**Status:** Proposed (owner confirmation required before Stage 2)
**Date:** 2026-10-05
**Deciders:** Project owner, system architect

## Context

§28: skills must be provider-independent, with a single authoritative source and generated/synchronised provider projections; drift should be detectable (Invariant 11). §29: roles have default skills, tasks declare required skills, and the router must ensure the selected runtime can access them. §30: skills are distinct from tools. Claude consumes skills as `.claude/skills/<name>/SKILL.md`; Codex consumes repository instructions (`AGENTS.md`) and provider-specific skill folders where supported.

## Decision

**D-1 Canonical format.** A skill is a directory `<name>/` containing `SKILL.md` with YAML front matter (`name, version, description, scope: PROJECT|KERNEL, applies_to_roles, requires_tools, tags`) and a Markdown body, plus optional `references/` and `scripts/` sub-folders. Kernel built-ins live in `src/walk/skills/builtin/<name>/`; project skills in `.ai/agents/skills/<name>/`. Project skills shadow built-ins by name. Skill names are kebab-case.

**D-2 Projections are generated by adapters, never hand-edited.** Each `ModelAdapter` exposes a `SkillProjector`. `SkillRegistry.project_all()` writes projections into the run's **worktree** (not the repo tree) at sandbox creation: Claude → `<worktree>/.claude/skills/<name>/SKILL.md` (+ copied `references/`, `scripts/`); Codex → managed section in `<worktree>/AGENTS.md` delimited by `<!-- walk:skills:start -->` / `<!-- walk:skills:end -->` listing each skill's description and inlining bodies of skills ≤ 4 KB, linking larger ones to `<worktree>/.walk/skills/<name>/SKILL.md`. Projection targets are added to the worktree's `.git/info/exclude` so they never enter commits.

**D-3 Drift detection.** `skill_projections` table and `.ai/agents/projections.lock.yaml` record `(skill, provider, target_path, content_sha256, generated_from_sha256)`. `walk skills check-drift` (also at startup and in `walk doctor`) reports: `missing` (canonical skill without projection), `modified` (projection hash differs from recorded → someone edited the projection), `orphaned` (projection with no canonical source). Drift is a `ConfigError` for `--strict`, otherwise auto-regenerated with a `CONTEXT_UPDATED` ledger event.

**D-4 Assignment and availability.** `AgentInput.skills = SkillRegistry.for_role(role, item.contract.required_skills)`; a required skill missing from the registry, or whose `requires_tools` are not available in the environment, blocks routing with `ConfigError` → work item `BLOCKED` with reason (§29).

**D-5 Versioning.** `Skill.version` is a `BehaviorVersion` (kind `SKILL`); project pins in `kernel-versions.yaml` select which built-in version is projected; skill changes are `MEDIUM` risk improvements (§104).

**D-6 Skills vs tools.** A skill may reference tools by `ToolName`; it never embeds credentials or executes anything itself. Scripts under `scripts/` are run through the normal shell tool and are subject to permission rules.

## Alternatives

- **Maintain Claude and Codex skill folders by hand:** rejected — guaranteed drift; violates single source (§28).
- **Project skills into the repository tree and commit them:** rejected — pollutes the game repo with provider artefacts and creates merge noise; worktree-scoped projections are reproducible from the canonical source at any time.
- **Serve skills via MCP resources:** deferred — Codex and Claude both read file-based skills today; MCP adds runtime dependency.

## Consequences

- Every adapter must implement `SkillProjector`; plugin adapters inherit the contract.
- Projections are regenerated per run (cheap: file copies) — no stale projections across model switches.
- `tests/skills/test_projection_roundtrip.py` asserts canonical → projection → hash stability for both providers.
